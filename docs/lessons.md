# Lessons learned — 0.1.0 文字階段

`deviations.md` 是**逐件**記錄:111 節,每一節是一個 bug 和它的理由。
這一份是從那 111 節裡歸納出來的**通則** —— 同一個形狀重複出現三次以上的,
才寫在這裡。

寫給以後的自己:進到圖片階段之前,先讀這一份。下面每一條都花了至少一輪
「使用者截圖 → 我猜 → 猜錯」才學到。

---

## 1. 同一個判斷有兩份實作,必然分岔

**這一條踩了六次**(§AS → §BY → §CH-2 → §CI-1 → §CL → §CX-2 / §CX-6)。
它是這個專案最貴的一個教訓,而且每次的偽裝都不一樣:

| 兩份分別在哪 | 症狀 |
| --- | --- |
| probe 自己算幾何 vs production 的 `coverRect`(§CH-2) | probe 全過,真站台蓋到圖 |
| `explainCandidate()` 沒模擬 `isAppChrome()`(§CI-1) | 63 段外殼被回報成「應該會翻」 |
| `captureRuns` 少了 `walk` 的 `ctx.seen()`(§CL) | 每 400ms 重掃整棵樹,頁面像卡住 |
| `hasMediaChild` vs `mediaSplitOf` 各有一把「多大算圖」的尺(§CX-2) | 24×24 圖示讓每個 `<h2>` 整段跳過 |
| `explainCandidate()` 沒模擬 sr-only 祖先與收折的 `<details>`(§CX-6) | 902 段被回報成「符合所有規則」 |

**規則**:

- 判斷邏輯只能有一份。要在別的地方用,就 import 它,不要抄。
- 除錯工具**必須跑同一份程式**。做不到就讓它明確說「我不知道」,
  不要給一個看起來合理的答案 —— **說謊的除錯工具比沒有除錯工具糟得多**,
  因為它讓每一次追查都從錯的前提出發。
- 走捷徑的路徑(`captureRuns`、`captureInlineText`)要**自己補上主路徑的每一道
  關卡**。少一道就是一個復活的 bug。

**怎麼避免下次再犯**:把判斷抽成純函式放在沒有 IO 的模組裡
(`upgrade.ts`、`queuelogic.ts`、`motion.ts` 就是這樣長出來的),
然後主路徑和除錯路徑都 import 它。抽不出來的,至少寫個測試比對兩邊的結論。

## 2. 沉默的失敗比錯誤的結果更難查

**沉默的成功和沉默的失敗長得一模一樣。** 這一條也踩了五六次。

- §CP-1:「按了沒反應」,而 log 裡**一行都沒有** —— 分不出「沒被呼叫」
  還是「呼叫了但集合是空的」,而這兩個要用完全不同的方法查。
- §CS:`chrome.runtime.sendMessage(...).catch(() => {})`,註解寫「下一次動作會重試」。
  對 `enqueue` 而言**沒有下一次動作**,那一塊從此停在 L0。
- §CR-1:worker 的 `post()` 也是空的 catch,而佇列在那之前就清掉了 —— 譯文直接消失。
- §DA-2:`text.length > MAX_UNIT_CHARS` 直接 return,一段 1576 字的引言
  不是失敗、不是跳過,**就只是不存在**。
- §CQ:區塊 `l1Queued = true` 之後沒有任何出口,既不會成功也不會失敗。

**規則**:

- **每一條 `return false` / `continue` / 空 catch 都問一次:被擋掉的東西,
  使用者看得到嗎?** 看不到的話,擋掉的理由要能事後回答。
- 使用者親手觸發的動作(按鈕、快捷鍵、選取)**一定要留下它做了什麼**,
  包括「什麼都沒做」。`translate-page` 現在無條件寫一則 diag。
- 按鈕要有回音。真的沒事可做時狀態列會說「沒有可以再升級的區塊」,
  而不是安靜。
- **不要讓任何狀態沒有出口。** 「卡住」不該是一個可以永久停留的狀態:
  看門狗 45 秒後要嘛撈回來、要嘛標成失敗(紅色、可重試)。

## 3. 量測工具會說謊,而且說得前後一致

瀏覽器的 API 在某些狀態下**每一種量法都回同一個錯的值**,
所以「換一種方法量」不會救你。

| 狀況 | 說謊的 API | 真話在哪 |
| --- | --- | --- |
| 收折的 `<details>`(§BG) | `getBoundingClientRect` / `getClientRects` / `getComputedStyle` **全部**回展開時的值 | DOM 本身:祖先有沒有沒帶 `open` 的 `<details>` |
| `display: contents`(§CH、§CX-1) | `getClientRects()` 永遠是空的,但子孫照常渲染 | 渲染出來的文字(`innerText`),或者直接豁免這個 display |
| Tailwind v4 的顏色(§BY) | `getComputedStyle().color` 回 `lab()` / `oklab()`,不是 `rgb()` | canvas:塗上去再讀回來 |
| 半透明背景(§BV) | `rgba(255,255,255,0.1)` 讀起來是白色 | 往上疊到不透明為止,自己做 alpha 合成 |
| sr-only(§AL) | 不是 display:none、opacity 是 1、`getClientRects()` 還回一個 1×1 | 特徵組合:clip / clip-path / 面積 ≤ 4px |

**規則**:

- 遇到「量到的值明明對,行為卻不對」,先懷疑**量測本身**,
  而不是繼續換算法。
- `display: contents` 和收折的 `<details>` 是兩個已知的說謊者。
  任何新寫的幾何判斷都要先問一次:這兩種情況下它會回什麼?
- 顏色不是字串,別用正規表示式追 CSS 的顏色語法 —— CSS 每年會多一種寫法。
- 幾何規則**不能只靠 jsdom 測**(它沒有 layout,`getBoundingClientRect` 一律回 0),
  一定要有真瀏覽器的 probe。

## 4. 診斷工具本身也是程式,也會有 bug

§CR 是這個專案最尷尬的一段:我看著 log 裡「五次 `queue-l1` 只有兩次配得到
`enqueued`」,差點把它當成「訊息掉了」的鐵證寫進修正。

真相是 content script 和 service worker 是**兩個不同的 JS realm**,
卻寫同一個 `chrome.storage.session` 的 key,各自「讀 → 合併 → 寫」,
後寫的把先寫的整段蓋掉。**匯出的 log 少了什麼,和發生了什麼完全沒有關係。**

而且 `clip-to-container` 一則就佔掉 300 格緩衝裡的 250 格 —— 它的守門條件是
「數字變了才寫」,而那個數字每次 flush 都在 2↔12 之間跳,等於沒有守門。

**規則**:

- **日誌的容量是有限的,寫進去的每一則都在擠掉別的東西。** 高頻的訊號
  要有真正的守門條件(看穩定的那個量,不看抖動的那個),否則降級給 `dbg`。
- 跨 context 的共享狀態不要共用 key。每個 scope 一把鑰匙,讀的時候合併。
- 同一個 context 裡的非同步寫入也要串成 chain —— 自己蓋自己一樣會發生。
- **一個數字看不出東西,兩個數字擺在一起才有對帳的可能。** 內容腳本說
  「5 塊在排隊」、worker 說「佇列是空的」,分開看都正常,並排就露餡。

## 5. read-modify-write 沒有序列化 = 隨機的資料遺失

§CY 和 §CR-1 是同一個病的兩個實例,而且我第一次(diag)修完之後
**沒有想到去檢查佇列有沒有同樣的問題**。

`enqueue`(訊息)、`reprioritize`(捲動)、`dropPage`(換頁)、`drain`(排程)
各自「load → 改 → save」,之間全是 `await` 邊界。交錯的結果是:drain 把做完的
batch 移出佇列存檔,捲動觸發的 reprioritize 拿著**舊版佇列**改完存回去 ——
做完的項目復活再跑一遍。快取擋住了帳單,擋不住浪費。

**規則**:

- MV3 裡任何「從 storage 讀 → 改 → 寫回」的路徑,只要有兩個以上的呼叫者,
  就要序列化(單一 promise chain / `mutateQueue()` 這種封裝)。
- 修好一處之後,**主動去找同構的其他處**。同一個錯誤模式很少只出現一次。
- 這條不只適用於程式。§DD:CI 把 zip 掛上 GitHub Release 之後,
  使用者送出了一份四分鐘前就打開的草稿編輯表單,asset 被洗掉了。
  **開著沒關的瀏覽器分頁也是一個握著陳舊快照的 writer。**

## 6. 規則的前提要能被推翻

好幾個 bug 的根源是一句**寫在註解裡、聽起來很合理、但實際上是錯的**斷言。

| 斷言 | 現實 | 節 |
| --- | --- | --- |
| 「段落不會有一千字」 | stratechery 的引言 1576 字,零個子元素 | §DA |
| 「`aria-hidden` 代表不是內容」 | 逐字動畫把**畫面上每一個字**標成 aria-hidden | §CU |
| 「文字全來自連結 → 那是按鈕列」 | 文章標題本身就是永久連結(每個 WordPress 版型) | §CZ |
| 「L0 是毫秒級的」 | 實測平均 3–8 秒,排隊 40 秒 | §AN |
| 「`<header>` 是站台外殼」 | `<article><header>` 是**文章的**頭尾(HTML 規格如此) | §CX-4 |
| 「sticky 的東西要整棵跳過」 | 那是寫在「動就先藏起來」機制之前的規則 | §CC |

**規則**:

- 用**結構性**的判斷取代**統計性**的猜測。「是不是容器」有明確答案
  (`hasContainerChild`:底下有沒有帶文字的 block);「是不是太長」沒有。
- 統計性的門檻(24 字、1000 字、20×20 px)只能當**最後一道防線**,
  要訂在「真實內容絕對到不了」的地方,不是「大部分內容到不了」。
  而且撞到它要留下痕跡 —— 撞到就代表有個結構沒想到。
- 註解裡的「一定 / 不會 / 只有」是未來的 bug 的種子。寫的時候問一次:
  我怎麼知道?能不能找到反例?

## 7. 自動的規則可以保守,使用者親手做的動作不行

同一條規則套在兩種情境上,是好幾個「按了沒反應」的來源。

- §CP-2:停留門檻不理會收折的 `<details>`(看不見的不必花錢),
  這是對的。但我把同一條抄進「翻譯這一頁」—— 使用者要的是「這一頁」,
  拿到的是「這一頁我現在看得到的部分」。
- §DA-3:hover 是被動的(滑鼠掃過就觸發),500 字上限是對的。
  選取是使用者拉了一段話明講「翻這個」—— 那和按按鈕同一類。
- §CO:停留門檻讓區塊留在 L0 是成本閘門,對的;但它留下一個沒有出口的狀態,
  整頁「完成」了其中十二塊卻只有 L0 品質。再按一次按鈕要能把它們升上去。

**規則**:成本閘門只約束**自動**行為。使用者花力氣觸發的動作,
預設是「照做,而且做完」。

## 8. 放寬了誰能成為單元,就要重新檢查誰在拿單元當量尺

§CF。這是「改動的漣漪」那一類,單獨列出來是因為它不直觀。

我把 sticky 子樹從「整棵跳過」改成「可以成為單元,但標記 pinned」,
結果是 `<button>` 變成了 `u1` —— 而捲動同步的哨兵剛好用「第一個單元」
當參考點,於是整片疊層跟著那顆按鈕跑到 header 上。

**規則**:改了「什麼可以成為 X」之後,搜一遍程式碼裡所有**假設 X 有某種性質**
的地方(第一個、最大的、一定在文件流裡、一定有 box……)。

## 9. 一次看整片,不要一次修一張截圖

§CI 和 §CX。使用者的原話是「這個測試 loop 太長了」,他說得對。

「截圖 → 修一個 → 再截圖」一輪只解一個形狀,**而同一頁上往往同時卡著五種
不同的原因**。改成:把整頁(後來是 37 站)掃一遍,把「看得見卻沒人接手的文字」
按原因彙總,一次看完再決定修哪些。

第一輪的結果:最大的一桶 902 段全部指向同一個病根(`display:contents`),
而那個病根從截圖上完全看不出來。

**規則**:

- 覆蓋率要有可重複執行的量法,而且**輸出要按原因分組**,不是按位置。
- 那份稽核就是回歸測試。改完偵測規則跑一次,看哪一桶變大了。
- 選網址要選**文章頁**,不是首頁 —— 偵測的難點在內文版型。

## 10. fixture 要裝著會弄壞它的東西

§CM。我的快照 probe 全過,真站台卻只套用 0/27 段 —— 因為**我的 fixture 裡
一個 `<script>` 標籤都沒有**,而 bug 正是「移除 script 之後 childNode 索引位移」。

**規則**:

1. 加規則的時候,fixture 同時加**正反兩例**(要翻的 / 不能翻的)。
2. 加完之後,**把修正暫時撤掉,確認 probe 真的會報錯**。
   一個永遠會過的測試等於沒有測試 —— 而且它會給你錯的信心。
3. fixture 要複製真站台的**髒**:`<script>`、內嵌樣式、動畫用的 wrapper、
   `display:contents`、折行。乾淨的 fixture 只證明乾淨的頁面可以動。

## 10-bis. 接縫兩側都對,壞的是接縫

§DF。視覺管線接完,單元測試全綠、probe 全綠、線上**零區塊**:
模型回了框、花了 4311 個 output token、沒有任何一層報錯。
病根是線上叫 `box_2d`、內部叫 `box`。

三層都沒有理由喊:API 做完了它的事、JSON 解析成功、
`sanitizeBlocks` 收到一堆不合格的東西回傳空陣列 —— 而**空陣列是合法結果**
(「這張圖沒有字」)。

單元測試抓不到,因為它餵的是內部形狀 —— 測的是「拿到 `box` 之後做得對不對」,
而 bug 在拿到之前。

**規則**:

- 資料跨過一個**改名 / 改形狀**的接縫時,測試要餵**上游的形狀**,
  不是下游的。把轉換抽成一支收上游形狀的純函式,測試才跨得過那條縫。
- 「空的結果」是最容易藏東西的地方:合法、沉默、看起來像正常運作。
  凡是「空」既可能是真相也可能是斷線的地方,**要有一條斷言分開兩者**。
- §DB-2 說「量測要走 production 的路」;§DF 說**production 的路也要真的
  走一次**。兩者都不是多跑一次單元測試能取代的。

## 10-ter. 量測要先量自己的噪音

§13-0。要決定縮圖上限,第一版的指標是「框的 IoU」。跑出來:
同一張圖、同樣尺寸,兩次 35 塊 vs 58 塊、IoU **0.48**。

那個 0.48 不是解析度的影響,是模型的隨機性。而我差一點拿它下結論 ——
用同一組數字可以論證「1536 夠用」,也可以論證「縮圖有害」,兩句都是噪音。

**規則**:

- **每個量測都要有一格「同樣的輸入跑兩次」**。那一格就是這個量測的解析度;
  比它小的差異不算差異。沒有這一格的比較表,看起來很專業,實際上不知道
  自己在看什麼。
- **指標要對「我們不在乎的變異」不敏感**。框會抖、切法會變(一塊還是兩塊),
  那些我們都不在乎;在乎的是「圖上這串字有沒有被讀到」。
  換成文字召回率之後,數字立刻穩定而且可解釋。
- 有些問題**現有的方法就是答不出來**(§13-2 的框漂移)。那時
  **留白比填一個假數字好** —— 假數字會被下一個人當成已知。

## 10-quater. 抄舊管線時,失敗路徑的兜底最容易漏掉

§DG。圖片管線是照文字管線寫的:佇列、退避、快取、成本閘門都抄了,
**唯獨漏了「沒有回音時誰負責把狀態交還給使用者」**。

結果是使用者第一次實際用就撞上:第三張圖之後全部卡在「辨識中」,
再滑上去也沒反應。三個病根疊在一起,而三個都是失敗路徑:

1. 執行中的工作還在佇列裡,而過期規則不看它在不在跑 ——
   10 秒的過期線,配上實測 17–70 秒的模型,**每一張都會被自己殺掉**
2. 丟掉工作時沒有通知另一側,對方的「進行中」集合永遠不會清
3. 節流的分支沒有 log、也沒有更新時間戳,等完立刻被判過期

**規則**:

- 新管線抄舊管線時,先問「舊的那條**流血換來**的是哪幾行?」
  那幾行通常不在成功路徑上,而是看門狗、對帳、逾時、通知對方。
- 任何「我送出去了」的狀態,都要有**兩個**出口:回應,以及**沒有回應**。
  只寫前者,那個狀態就會變成永久的。
- 一個常數(10 秒的過期線)和另一個實測值(17–70 秒)在同一份文件裡
  互相矛盾,而我沒發現 —— **門檻類的常數要和它要擋的那件事的實測值
  放在一起看**。

## 11. 模型輸出是敵意輸入,但也不要誤殺

§V、§CT、§CV。id 紀律的三層防線(echo 對位、重複 id、缺 id)是必要的,
但**判定要精準**:

- `echo-swap`(echo 對到同批另一筆的原文)是 batch 內對滑的直接證據,
  整批不可信 → 整批丟棄。
- `echo-mismatch`(只是沒照抄)多半是模型自作主張改了引號或大小寫 →
  正規化之後再比,不要誤殺。
- `duplicate-id` 記在**第二次**出現的那一筆上,而第一次早就進了 results ——
  **那一塊其實翻好了**。上一版照樣把它當失敗送出去,而 failures 在 results
  之後才到,於是一塊翻得好好的字被降級成紅色。使用者的話是「要多按幾次才行」。
- `missing-id` 原封不動丟回同一個佇列補一次(不切小、不改協定),上限一次。

**規則**:

- **有譯文的區塊永遠不是失敗的區塊。** 這條不變式便宜,而且它防的是
  下一條還沒寫出來的路徑。
- 誤殺的代價常常比漏抓高:誤殺會讓正確的結果變紅、要使用者手動救援。
- 重試上限要有,而且要明說。無人看管的重試迴圈會安靜地一直花錢。

## 12. 一個 bug 兩個症狀;兩個症狀不一定同一個 bug

§BF 是前者:「疊層跑到左上角」和「盒子被撐得很大」是同一個病根
(元素沒被畫出來時 rect 全 0)。§CL 是後者:「一直卡在 missing-id」
其實是**兩個各自獨立的錯覺**疊在一起。

**規則**:先問「這幾個症狀能不能用一個原因解釋」,能就先找那個原因;
但不要為了優雅硬湊 —— 湊錯了會修一個、留一個,而留下的那個更難查,
因為你已經「修好了」。

§AI。「按鈕與 widget 要不要翻」我想了很久,後來去看其他翻譯外掛怎麼做 ——
它們的答案是「整個不翻」。那不是我要的,但知道**別人選了什麼、代價是什麼**

**規則**:在自己發明機制之前,花十分鐘看看這個問題別人怎麼解。
不是為了抄,是為了知道自己在偏離什麼。

## 14. 這個專案的具體結論(給圖片階段參考)

- **不改動 DOM/CSS 是對的約束**,它逼出了 closed shadow DOM + document 座標
  + `pointer-events: none` 這條路,也讓「匯出疊好的 HTML」變成一件需要
  重新實作的事(§CK)—— 因為原始頁面上根本沒有那些譯文。
- **L0 + L1 兩段式的價值不在速度,在「先有東西可讀」**。L0 實測是秒級不是
  毫秒級(§AN),真正的收益是使用者不用盯著空白等。
- **停留門檻(1.5 秒)是最有效的成本控制**,但它必須配上一個手動出口。
- **狀態要說得起「完成」**。長文頁面永遠有沒捲到的區塊,拿「整頁還有 pending」
  當忙碌判準的話,狀態列永遠不會說完成(§BA、§CN)。
- **每個網域記自己的設定**是對的:技術文件站留在點閱,長文站留在全開。
- 圖片階段開始前,先想清楚「圖裡的字翻了要怎麼**還原成看得懂的版面**」——
  文字階段的每一個坑幾乎都是幾何問題,圖片只會更難。

## 16. 抄來的視覺參數要量,而且要在**會讓它失效的那一端**量

`brightness(1.16)` 是從 sukemu 抄過來的 veil 配方。我把它寫進規格的
「可抄清單」時附了一句理由:「把該區原文壓暗退後」。

那句話是**推論**,不是量測,而且只在淺底上成立。brightness 是乘法:
白底乘 1.16 還是白、黑字乘 1.16 還是黑 —— 淺底黑字看起來有效,是因為
上面那層淺色漸層把黑字吃掉了一截,不是 brightness 的功勞。深底白字上
兩端都不動,對比一點都沒掉。使用者在深色 bar chart 上看到的就是這個。

三個可以一般化的點:

1. **抄過來的參數要連著它的素材一起抄。** sukemu 的素材是掃描頁面
   (淺底深字);kasanemu 的素材是網頁上任何圖。同一組數字換一批素材
   就換一個結果,而「這組數字在原專案有效」不構成證據。
2. **量測要挑會讓它失效的那一端。** 我如果只在白底圖表上看一眼,
   會覺得沒問題 —— 而那正是我做過的事。`probe-veil.mjs` 現在固定量四種
   底色(深、淺、中灰、彩),**四種同時要過**;只在一端有效的配方
   進不來。
3. **「這是視覺,量不出來」是錯的。** 可讀性可以量:原文殘留對比、
   譯文對比,兩個數字、四個素材、一支 probe。花了一次量測的功夫,
   換到的是這一類 bug 以後在 `npm run check` 就停下來,不必等使用者截圖。

同一支 probe 也把另一件事釘住了:那次回報有兩個症狀(「不能看」與
「不統一」),而它們是**兩個 bug**(§12 已經寫過一次)。第一個是濾鏡方向,
第二個是門檻的**作用域** —— 逐塊判斷時每一塊都對,合起來是兩套視覺語言。
規則正確不代表規則用對了地方。

## 17. 復原的鷹架不會自己跟著功能走

同一條教訓咬了三次,每一次的症狀都是「卡住,沒有回應」:

| | 漏掉的東西 | 症狀 |
|---|---|---|
| §CO / §CY | L1 看門狗、兩側對帳 | 文字停在半路 |
| §DG | 丟工作時通知 content、節流時記 log | 圖片永久卡住 |
| §DI | **alarm、timeout、旗子的解耦、孤兒的過期線** | 圖片還是卡住 |

三次都是同一個動作:抄舊管線的時候,**成功路徑的結構抄得很完整,
失敗路徑的兜底一個都沒抄**。後者比較不顯眼,而且正是舊管線流血換來的
那一部分 —— 它們在程式碼裡看起來像是可有可無的雜訊。

具體到 §DI,漏掉的四樣東西有一個共同點:**它們都不在功能的敘述裡**。
「hover 圖片 500ms 送 L0,回來畫加註」這句話裡沒有 alarm、沒有 timeout、
沒有孤兒。它們只在「這件事沒有照著發生」的時候才存在。

所以複製管線的時候,值得問的不是「這個功能要做什麼」,而是:

1. **誰把它叫醒?** service worker 隨時會被回收,記憶體裡的一切都沒了。
   佇列活著不等於有人會去看它。
2. **每一個 `await` 都會結束嗎?** 裸的 `fetch()` 不會。一個永遠不 settle
   的 promise 不只卡住自己,還會扣住所有 `await` 在它前面的東西。
3. **這面旗子什麼時候放下?** `if (busy) return` 加上在無界的 await 後面的
   `finally`,等於一次故障換永久停擺。
4. **沒有人在跑它的時候,誰收屍?** 「使用者明確點的,慢也要做完」的前提是
   還有人在跑它。

## 17-bis. 有順序關係的常數要住在一起

`FETCH_TIMEOUT_MS < VISION_TIMEOUT_MS < ORPHAN_MS + alarm < IMAGE_WATCHDOG_MS`。

這四個數字原本散在三個檔案裡(worker 兩個、content 一個),而它們是一組
**有順序的**數字:由內而外遞增,每一層都要留給下一層說話的機會。

順序錯了不會有任何症狀 —— 直到使用者先看到「沒有回應」,而 worker 的真正
原因姍姍來遲,兩邊各說一套。這種錯沒有堆疊追蹤,也沒有失敗的測試,
只有一個看起來很像網路問題的使用者回報。

分散的時候,那條不變量**沒有任何地方寫得出來**:每個檔案裡的數字單獨看
都很合理。搬到同一個檔案之後,常數的位置本身就是宣告,而測試可以直接
把順序釘住 —— 不需要跨檔案的靜態分析,只需要一個 `assert.ok(a < b)`。

通則:**當兩個常數的關係比它們的值更重要時,它們屬於同一個檔案。**

## 18. 每一層都通過了自己的測試,而使用者拿到的是一堆讀不到的圓點

`setActivePin` 只做了一半:圓點會放大,但**貼片從來沒有實作過**。
規格寫了(§2.3「hover pin 出貼片」),沒有任何一層抓到。

看每一層驗了什麼:

| 層 | 驗的東西 | 結果 |
|---|---|---|
| 單元測試 | `pinAt` 命中測試算得對嗎 | ✅ 對 |
| probe | `placed` 陣列裡有幾個 pin | ✅ 15 個 |
| 型別 | `setActivePin(n: number)` 呼叫得對嗎 | ✅ 對 |
| 使用者 | **上面有字嗎** | ❌ 沒有 |

每一層問的都是「我這一段做對了嗎」,**沒有一層問「使用者最後看得到什麼」**。
這不是覆蓋率不夠 —— 再加十個 `pinAt` 的測試也抓不到。缺的是一個**問結果
而不是問步驟**的斷言:「畫出來的那片貼片,上面有沒有譯文」。

實作方式很土,但那正是重點:probe 攔 `attachShadow` 拿到 closed root,
直接 `querySelector('.ipop')?.textContent.includes(zh)`。動的是 probe 那一側,
production 不必為了被驗而開後門。

通則:**每個功能至少要有一條斷言,問的是使用者看得到的那個結果**。
「資料算對了」和「東西畫出來了」之間永遠有一段沒人負責的路。

## 18-bis. 同一個假設錯三次,是因為它從來沒被寫成一句話

veil 修了三版,每一版都在調參數:

1. `brightness(1.16)` —— 方向錯。
2. `contrast(.2)` —— 方向對了,但把底圖一起壓沒了。
3. 玻璃 + 貼片 —— 換掉假設本身。

前兩版共用一個沒說出口的前提:**譯文站在 veil 收出來的那片底上**。
只要這個前提還在,調參數就是在「讓那片底同時服務兩個矛盾的目的」——
既要壓住原文(要暗、要平),又要托住譯文(要亮、要可預測),
而底下是什麼圖我們不知道。無解。

第三版把兩個目的**拆給兩個東西**:玻璃壓原文(靠模糊,不動明度),
貼片托譯文(自己的底,和圖無關)。參數瞬間變得好調,因為每個參數
只服務一個目的了。

看得出「這是同一個假設又錯一次」的訊號:**修了兩次還在同一個檔案的
同一行調數字**。那通常不是數字的問題。

## 19. 每一段都對,錯在**段與段之間**

`(§DK)` 那片 chip:畫出來了、`pointer-events: auto` 開了、`onclick` 綁了、
`action` 送得出去 —— probe 實測按下去真的會觸發。使用者拿到的仍然是
「那個 tip 不能點」,因為**滑鼠走過去的那半秒**沒有任何一層在看。

這和 §18(每一層都通過了自己的測試)是同一種病的兩個面:

- §18 是**縱向**的斷層:資料算對了,但沒有人驗它畫出來沒有。
- §19 是**橫向**的斷層:兩個狀態各自都對,但沒有人驗**從這個到那個**
  那段路走不走得通。

橫向的斷層特別難發現,因為它不在任何一個模組裡 —— 它在
「滑鼠離開圖片」和「滑鼠到達 chip」中間那個沒有名字的狀態。而那個狀態
在程式碼裡完全不存在:`move()` 只認得「在圖上」和「不在圖上」。

找它的方法是**照使用者的動作寫一條測試**,而不是照模組的邊界:
「滑到圖上 → 滑到 chip 上 → chip 還在嗎 → 按下去 → 開了嗎」。
這種測試橫跨三個模組,看起來不像單元測試,但它是唯一會紅的那一條。

## 19-bis. 新測試要先確認它會紅

修完 §DK 我寫了四條測試,全綠。然後把修正拿掉重跑 —— **還是全綠**。

我的斷言是同步的,而修正的另一半(220 毫秒的寬限期)剛好把症狀蓋過去。
測試驗的是「不會馬上消失」,而使用者的問題是「停著讀完那行字它就沒了」。

**一條從來沒紅過的測試,和沒有測試的差別只是它會消耗 CI 時間。**
寫完之後把修正拿掉重跑一次,是最便宜的驗證,而且它同時驗兩件事:
測試抓得到這個 bug,以及**你以為的病根就是真的病根**。

## 20. 收起來可以有很多入口,放回來只能有一個出口

Alt 按下去收了兩樣東西(文字疊層、圖片加註),而「放回來」在三個地方
各寫了一份(keyup、視窗失焦、按下別的鍵)。三份都只做了一半 ——
文字回來了,圖片加註沒有,而且永遠回不來(§DL-2)。

這是**對稱性的維護成本**問題:每加一個「收起來」的動作,就要記得同步
三個「放回來」的地方。沒有人記得住,所以它一定會爛。

修法不是補那一行,是把三個出口收成一個 `restoreLayer()`。
之後再加第四種收起來的方式,只要改一個地方。

判斷標準很簡單:**如果一個狀態有 N 個入口和 M 個出口,而 N、M 都大於 1,
那就是遲早的事。** 把 M 壓到 1。

而且要為「出口根本沒被呼叫」留一條保險。keyup 會掉(焦點被搶走、
切分頁、作業系統攔截),`blur` 接得住大部分但不是全部。剩下的靠
`mousemove` 上的 `altKey` —— 使用者想看回譯文時本來就會動滑鼠,
所以那顆事件必然會來。**恢復的保險要掛在「使用者一定會做的動作」上,
不是「理論上應該會發生的事件」上。**

## 20-bis. 認得出一個東西,不代表想過它的所有後果

`hasNativeZoom()` 早就認得 ClickHouse 壓在圖上那顆透明按鈕 ——
整個函式就是為了認出它而寫的(認出來就不出我們自己的放大入口)。

而**同一顆按鈕會擋掉 hover**,沒有人想過。於是那個站的圖在點開
lightbox 之前完全不會翻,而我們手上明明有「這裡有一顆透明按鈕」的資訊。

一個外部現象被寫進程式碼裡的時候,它通常只被當成一件事的證據。
值得多問一句:**這個現象還會影響什麼?** 特別是當它的本質是
「有東西蓋在上面」——那幾乎必然同時影響命中測試、事件目標、
以及任何依賴 `closest()` 的判斷。

## 21. 把「碰巧同時出現的東西」當成識別條件

Wired 的文章 header 有兩個性質:它在 `<article>` 裡面,而且它裝著文章的
標題與導言。修 §CH 時我挑了第一個當條件 —— 因為它好寫,一行 `closest`。

但讓它「不是站台外殼」的是**第二個**性質。第一個只是碰巧同時成立。

於是同一個 bug 換一種寫法就復發:靜態網站產生器把 h1 和導言放在頂層的
`<header>` 裡,外面沒有 `<article>`,整個標題區又消失了(§DM)。

判斷自己有沒有犯這個錯,有一個很直接的問法:**「如果這個條件不成立,
但那個性質還在,結論該不該一樣?」** 沒有 `<article>` 但仍然裝著頁面的
標題與導言 —— 結論當然一樣。那就表示條件挑錯了。

好的識別條件通常比較難寫(這次要同時看標題與散文長度,還要排除導覽區),
而那個「比較難寫」本身就是訊號:它在描述**那個東西真正是什麼**,
不是在描述它剛好長在哪裡。

## 21-bis. 規則改動沒有前後對照,等於沒有驗

改完 `isAppChrome` 我跑了 37 站的稽核,輸出是「37/37 站跑完」。

那句話**在我把整個網路的頁首都翻掉的情況下也會印出來**。單看改後的數字
分不出「修好了」和「炸了但沒 crash」。

所以要 stash 起來再跑一次:

```
git stash && node scripts/audit-sites.mjs > before.txt && git stash pop
```

逐行 diff 之後才看得到真正的結果:一站變好(github.blog 漏 16%→14%),
其餘 33 站逐字相同,沒有新的站掉進「漏 >15%」名單。

這和 §DK-1(新測試要先確認它會紅)是同一條紀律的兩半:
**測試要證明它抓得到壞的,稽核要證明它分得出好的和壞的。**
兩者都需要一個對照組,而對照組永遠是「把修正拿掉再跑一次」。

## 22. 範圍要跟著證據走,而證據要自己去找

§DM 的修法是對的,但範圍是照著**當時手上那一個例子**畫的:
只補 `<header>`,散文只認 `p / blockquote / li / dd`。

隔天同一個站的**頁尾**又中一次。爬完整個站之後才看到:同一個形狀在
`<header>` / `<aside>` / `<footer>` 上各出現一次,而且散文還會裝在
`<div>` 裡(§DN)。

問題不在我修得不夠廣 —— 修太廣是另一種錯。問題在於**我沒有去找證據**,
只用了使用者遞過來的那一個。一個例子能告訴你「這裡有問題」,
不能告訴你「問題有多大」。

所以先寫 `audit-tree.mjs`:爬一個站的所有子路徑,把原因按「出現在幾頁」
彙總。**同一個原因橫跨多頁 = 那是版型層的規則問題,不是那一頁的怪癖** ——
這句話就是這支工具的全部價值,其他都是實作細節。

一次爬取抓到四個問題,使用者只回報了其中一件。而修好之後,37 站稽核裡
theverge 從漏 60% 變 0%、apnews 從 20% 變 0% —— 使用者回報的是一個
小站的頁尾,修好的是一整類版型。

## 22-bis. 稽核自己說謊,比沒有稽核更糟

爬站報表最上面第二大的原因是「95 段 SVG 文字沒人接手」。那是**假的**:
`auditInPage` 從來沒呼叫 `findSvgTexts`,而 SVG 裡的字有自己的管線。

假警報的代價不是「多看幾行」,是:

1. 它把 5 頁的漏字率推過門檻,那幾頁的**真**問題被歸類成「這頁本來就爛」。
2. 它排在報表第二位,而真正的 header / aside / footer 問題排在它後面。

工具的可信度是它的全部價值。一份會說謊的報表,讀的人會開始「憑印象
過濾」——而那正是這份報表本來要取代的東西。

新增一個判定層(SVG、圖片、UI 標籤)的時候,要同時問:
**稽核知道這一層存在嗎?** 不知道的話,那一層處理掉的東西
會全部被算成漏掉。

## 23. 外部系統說的話是輸入,不是事實

`Content-Type` 是伺服器**宣告**的東西,不是檔案**是**什麼。這兩者在
Google Cloud Storage 上就不一樣:每一張 WebP 都標成
`application/octet-stream`(§DO)。

瀏覽器早就知道這件事 —— 它嗅 bytes,不信 header,所以圖片顯示正常。
我們的程式碼把那個字串當成事實,原樣轉給了下一個系統,而下一個系統
比較嚴格。

這和 §11(模型輸出是敵意輸入)是同一條:**任何跨越系統邊界進來的
描述性資料,都要用手上的實體驗證一次**。差別只在這次的來源是伺服器
不是模型 —— 而伺服器「應該」正確這個直覺,正是它比模型更容易漏掉的原因。

判斷哪些欄位屬於這一類,有一個問法:**這個值是誰算出來的,他有沒有
動機或機會弄錯?** `Content-Type` 由上傳者設定、由 CDN 轉發、由物件儲存
預設填 —— 三個環節,沒有一個以「正確」為目標。

## 23-bis. 截斷訊息的時候,先想清楚要留哪一半

錯誤回應是 `body.slice(0, 400)`,而 API 的錯誤 JSON 長這樣:

```
{\n  "error": {\n    "code": 400,\n    "message": "Unsupported MIME type: …
```

外殼佔掉前 50 個字,診斷再截一次之後,使用者看到的是
`{"error":{"code":400,"message":"Unsupported …` —— **恰好停在有用的那個字前面**。

於是使用者能說的只有「圖形功能好像出錯了」,而 log 上沒有別的線索。
一個查得很快的 bug(一行 JSON.parse 就指到病根)變成要抓封包才知道。

通則:**截斷要截在結構上,不是長度上**。有結構的東西(JSON、堆疊追蹤、
HTTP 回應)先解出那個欄位再截;`slice(0, N)` 只適合已經是一句話的東西。

## 24. 「拿掉這個」之前,先確認它當初買到了什麼

使用者說那片白像 OK 繃,要拿掉。它確實醜 —— 但它是 §DJ-2 量出來加上去的,
買到的是深色圖表上 1.8:1 → 7.7:1 的譯文對比。

直接照做就是把一個**量過的**東西換成一個**看起來比較順眼**的東西,
而下一輪回報會是「深色圖上的字看不清楚」——回到三版之前。

所以先掃一遍:直接拿掉、膜加濃、換光暈、羽化 —— 五個配方四種底色。
結果是拿不掉(膜濃到不像玻璃都還差一截),但**抱怨的其實不是那片白,
是它的邊**。同一片白模糊掉,對比一模一樣而 OK 繃感消失。

通則:**使用者描述的是症狀,不一定是病灶**。「拿掉 X」要先問
「X 當初解決了什麼」,答案常常是「X 的某個屬性解決了問題,而另一個屬性
造成了抱怨」——那就兩個都留不得也兩個都拿不得,要拆開。

## 25. 加註的預設不該是「全部蓋上去」

一張 bar chart 上 18 個加註,十五個顯示的是和底下一模一樣的字。

那不是 bug,是**預設值錯了**:管線的預設是「模型回了什麼就畫什麼」,
而正確的預設是「**只畫改變了什麼**」。差別在密集的資訊圖上非常大 ——
數值、產品名、代碼、軸標籤在圖表上佔絕大多數,而它們全部不需要翻。

同一條在別的地方也成立:diff 只顯示改動的行,版本控制只存差異,
而加註層蓋的應該只有**譯文和原文不同**的地方。蓋住原圖是有成本的
(遮蔽、糊化、注意力),而成本要換到東西才付得下去。

實作只有兩行判斷,難的是想到要問這個問題 —— 而使用者一句
「疊了沒意思」就問完了。

## 25-bis. 「不同」不等於「值得」

§25 的規則是「只畫改變了什麼」,實作成 `原文 !== 譯文`。
下一輪使用者指著 `5x` 說「其實也不用翻了」—— 而 `5x` → `5倍` 確實不同。

規則沒錯,是**判準只有一半**。「要不要蓋」其實是兩個問題:

1. 換到了東西嗎?(`5x` → `5倍`:換到一個字,有)
2. 換到的東西**大於成本**嗎?(蓋掉整個數字換一個「倍」字:沒有)

第一版只問了第一個,因為第一個可以用相等判斷寫完,第二個要定義成本。
偷懶的地方通常就是這樣露出來的:**能被一行程式碼表達的那半個問題,
會被當成整個問題**。

第二個問題最後也只是一行(字母數 ≤ 2 且含數字),但它是**估價**不是比對 ——
所以它需要界線,而界線需要兩側都有測試。

## 26. 硬邊會排隊

§24 把譯文貼片的硬邊化掉了,量測顯示對比一分沒掉,收工。
下一輪使用者說:毛玻璃也是方的。

貼片還在的時候,veil 的邊框沒人抱怨 —— **不是它當時可以接受,
是它當時不是最刺眼的那個**。拿掉排在前面的,後面的自動遞補。

這解釋了為什麼視覺回報常常一輪只給一件事:使用者不是慢慢想到的,
是**看到的東西真的變了**。所以做完一輪視覺修正之後,值得主動問
「現在畫面上還剩幾個硬邊 / 幾個獨立物件」,而不是等下一輪回報。

這一輪清出來的清單:圓角矩形、1px 邊框、上緣白高光、外投影 ——
四個都在說同一句話「這是貼上去的另一個物件」,而它們全部可以拿掉,
因為訊息本身(這裡有加註)已經由密度說完了。

## 26-bis. 排隊的不一定是硬邊,也可能是密度

§26 說「拿掉最刺眼的那個,後面的自動遞補」,舉的例子是硬邊:
圓角、邊框、高光、投影。這一輪遞補上來的東西**沒有邊**。

深色卡片上的加註實際是四階:深卡 → 霧 → 白貼片 → 橘字。
每一階都是軟的,但**四階本身就是一個形狀** —— 眼睛認得出「那裡有一塊
和別的地方不一樣的東西」,即使它一條硬線都沒有。

量測差點讓我修錯地方:膜的外緣量出來是 1.02:1(等於看不見),
照著數字走會得到「使用者看錯了」的結論。使用者沒看錯,是**我量的東西
不是他在看的東西** —— 我量的是最外面那一階,他看的是四階疊起來的輪廓。

通則:當量測說「沒問題」而使用者說「有問題」,先假設**量錯了對象**,
不要先假設對方的感覺不準。找出他實際盯著的是哪一塊,再去量那一塊。

## 27. 靠 DOM 順序成立的規則,重疊的那天才會露餡

「玻璃在下、字在上」以前是對的,但它是**巧合對的**:玻璃是文字塊的子元素,
所以只要兩塊不重疊,誰先畫都一樣。一重疊,下一塊的玻璃就蓋掉上一塊的字。

這種 bug 有個共同的形狀:**規則在單一元素的尺度上成立,在整層的尺度上不成立**。
單看一塊,結構完全正確;要兩塊同時出現才錯。所以單元測試看不到、
單塊的 probe 看不到,只有真實素材夠擠的時候才看得到。

修法也有共同形狀:**把「每個各自一份」改成「整層一份」**。
玻璃排成一層、字排成一層,順序就不再取決於誰和誰重疊。

順帶學到的:不要用 `z-index` 修。這個專案的 `.iblk` 在「掀起來看原圖」的
過場裡會拿到小於 1 的 `opacity`,那 160ms 之內每個塊都是自己的堆疊脈絡,
`z-index` 完全失效。**結構上的順序不挑時機,z-index 挑。**

## 28. 承諾寫在一個地方,兌現寫在另一個地方

失敗的 chip 上寫著「再點一次重試」,而它點不下去 —— 因為文案在一張表裡,
「能不能點」在三個呼叫點的第四個參數裡,而那三個呼叫點都沒帶。

值得記的不是「忘了傳參數」,是**這種 bug 測不到的原因**:
測試問得出 chip 上印了什麼字,問不出那句話在承諾什麼。
文案是資料,行為是程式,兩邊沒有任何東西逼它們一致。

修法不是補傳參數(那只會等下一個呼叫點再忘一次),是把承諾和兌現
**綁進同一個值**:`{ text, retry }`。之後想寫「點一下重試」就一定要
同時宣告 `retry: true`,不然那句話寫不出來。

通則:**只要文案在描述一個動作,那個動作就要和文案同生共死。**
按鈕的標籤和它的 handler、錯誤訊息裡的「請重試」和重試的入口、
文件裡的指令和它真的存在 —— 都是同一件事。

## 29. 「有沒有」和「是哪一種」是兩個問題

`inFlight` 是一個 `Set<url>`,兩個地方在用它:

- hover 防抖問「這張圖**有沒有**請求在飛」——對的。
- Alt+click 升級問的其實是「**有沒有已經在升級**」——而它只問得到前者。

於是免費檔還在跑的時候按升級,會被當成「已經在飛了」直接吞掉:
`return true`(所以連結也不會走),而且什麼都沒送出去。

集合退化的方向永遠是同一個:**一開始只需要「有沒有」,後來多了一個
需要「哪一種」的呼叫者,而它將就著用了現成的那個答案。**
將就的當下不會壞,因為那時候只有一種;壞在第二種出現的時候,
而第二種出現時沒有人回頭看第一個問題還夠不夠用。

## 30. 修好一個零件,不等於修好那個形狀

玻璃蓋到字,修法是「玻璃搬成一整層」。下一輪:白貼片蓋到字。

同一個形狀:**一塊自己帶著它的裝飾,於是裝飾跟著那一塊的層走**。
我修的是「玻璃」這個零件,而不是「加註由好幾個獨立的塊組成,
每個塊裡的東西都會蓋到別的塊」這個結構。所以剩下的那個零件原地不動,
等著下一輪被回報。

使用者的一句話比我的修法完整:「字在最上層,只能被字蓋到。」
那是一條**不變式**,而我做的是一次修補。不變式管得住所有零件,
包括還沒加進來的那些。

通則:回報進來的是**一個零件**,要問的是**它屬於哪一個形狀**,
然後把那個形狀裡的**每一個**零件都數一遍。數得出來就一次修完,
數不出來就先寫下不變式,讓它去管。

而不變式要進 probe —— 它才是那個「還沒加進來的零件」也管得到的東西。

## 31. 互相指名道姓的東西,沒有人在維護那條線

這個專案的註解寫「§DR-1」,文件寫「`npm run probe:veil`」、
「`scripts/render-veil.mjs`」、「271 個測試」。這些指名**全部沒有任何
東西在驗**:改個檔名、刪一支腳本、多加一條測試,指過去的那一端就變成
謊話,而且**它看起來和真話一模一樣**。

寫了一支 `audit-docs.mjs` 之後,第一次跑就掃出六處。其中兩處是
**稽核自己錯了**(標題寫成 `## AN.「L0…` 沒有空格,而我的正規式要求
句點後面一定有空格;另外兩個路徑指的是別的 repo,文件裡明講了)——
這件事本身是 §22-bis 的重演(就在這份文件裡):**稽核自己說謊,比沒有稽核更糟**,
所以先確認它會紅,再相信它說綠。

真的對不上的是四處散文:三份規格的「狀態」行還寫著「尚未實作 / 待啟動 /
圖片是下一步」,README 寫著「Phase 2 圖片翻譯不做」。

**分界線很清楚**:名字、數字、路徑、編號機器驗得出來,而**散文只有人讀得出來**。
所以稽核只查前者,而後者要在每次「這一階段做完了」的時候當成一個步驟 ——
它不會自己冒出來提醒你。

## 32. 一筆工作的測試,測不到佇列

「排隊超過十秒就丟」這條規則有測試,而且是綠的:

```ts
const q = [job({ url: 'a', at: 0 })];
assert.equal(nextJobs(q, new Set(), STALE_L0_MS + 1).drop.length, 1);
```

一筆工作、放著十秒、丟掉 —— 完全合理。**少的是第二筆工作**,
而「佇列裡有第二筆」正是這條規則唯一會出錯的情況:併發是 1,
所以第二筆的等待時間由第一筆的長度決定,和使用者想不想看毫無關係。

這和 §27(「靠 DOM 順序成立的規則,重疊的那天才會露餡」)是同一個形狀:
**規則在單一元素的尺度上成立,在整批的尺度上不成立。**
單看一筆,對;要兩筆同時存在才錯。

所以佇列的測試至少要有兩筆,而且其中一筆在跑 —— 那才是佇列的最小形狀。
一筆的佇列不是佇列,是一個變數。

## 33. 碼錶量的是什麼,要說得出來

「排隊超過十秒就丟」想問的是**使用者還想不想看**,量的是**前面還有幾張**。

寫的時候那兩件事看起來是同一件:等很久 = 大概不想看了。
但那個等號只在**併發夠大、佇列很短**的時候成立,而這裡併發是 1、
一張要四十秒 —— 等號當場斷掉,規則就變成「除了第一張全殺」。

通則:**每一個時間門檻都要能回答「這幾秒是誰的幾秒」。**
是使用者的注意力?是網路的延遲?是佇列前面那些人的工作量?
答不出來的話,那個數字遲早會在某個負載下代表另一件事。

而它的替代品常常不是「換一個數字」,是**換一個量綱** ——
這裡換成了張數:排幾張是使用者決定的,排多久是我們決定的。

## 34. 計算值不是使用值

`getComputedStyle(body).overflowX` 回報 `hidden`,而 body 一格都沒裁 ——
因為 CSS 把 body 的 overflow **傳播到視窗**了,body 自己當作 `visible`。
計算值(computed value)和使用值(used value)是兩件事,
而 `getComputedStyle` 這個名字只承諾前者。

會踩到是因為讀 CSS 的時候,腦子裡想的是「這個元素現在的行為」,
拿到的卻是「這個屬性算出來的值」。多數時候兩者一樣,所以這個差別
平常不存在 —— 直到遇到有傳播、有繼承、有 used-value 特例的那幾個屬性
(`overflow`、`width: auto`、`display` 在 flex 子項上的 blockification…)。

**驗的方法比記住規則可靠**:body 真的在捲的話 `body.scrollTop` 會動。
它永遠是 0 而 `scrollHeight` 有 6117,那就不是它在捲。
量一個**行為**,不要只讀一個**宣告**。

## 35. 「全部都做了」和「全部都被藏了」在 log 上長得一樣

診斷寫著「總 63 · L1 60 · 待翻 0 · 失敗 0」,而使用者看到的是一片原文。
兩邊都沒說謊 —— 統計數的是**翻譯管線**,而 bug 在**顯示**那一段。

log 裡其實有:

```
clipped-overlays {"checked":19,"hidden":19}
```

檢查幾塊藏幾塊。但這一則平常也長這樣(捲到一半、輪播的另一份),
所以它從來沒有被當成異常 —— **它缺的是一個比例的概念**。

通則:凡是「處理了 N 個、其中 M 個被跳過」的 log,
**M/N 接近 1 本身就是訊號**,值得在那一則裡直接說出來。
不然它會安靜地待在正常的那一堆裡,而使用者的症狀和它對不上號。

## 36. 同一條規則寫了兩次,只有一次被用到

「這個橫著的東西夠不夠寬,才算得上一條列?」——
`pinnedBottom()` 裡早就有這個判斷(`r.width >= 框寬的一半`),
寫的時候是為了「容器底部釘著的那一列」。

而 `chromeBand()` 問的是同一件事,只是換到視窗的尺度上,它卻沒有那條判斷 ——
於是一個 25% 寬的黏著側欄被當成頁尾,半個視窗的譯文被裁掉(§DY)。

值得記的不是「忘了複製一行」,是**當時沒有把那條判斷認出來是一條規則**。
它長得像 `pinnedBottom` 內部的一個細節,而它其實是
「**什麼東西算是門面**」這個問題的答案,而那個問題有兩個提問者。

徵兆:兩段程式在回答同一個問題,而只有一段有完整的答案。
找法也很直接 —— 修好一個地方之後問一句
「**還有誰在問同一個問題**」,然後真的去看那個地方。

## 37. 症狀一樣,不代表病因一樣

使用者的回報是「又出問題了 一樣沒翻」,同一頁、同一個症狀。
而上一次的病因(祖先的 overflow 被誤判)**確實已經修好了** ——
這份 log 裡 `hidden: 0`,證據明確。

如果因為「症狀一樣」就先假設是同一個 bug 復發,會花很久去證明一件已經對的事。
反過來:**先確認上一次的修正還在生效**,確認了就把它整個排除,
剩下的線索才浮得出來 —— 這次浮出來的是一則出現 47 次、
而且數值剛好是視窗一半的 log。

「剛好是某個上限」是很強的訊號:**那代表夾住它的那條線正在起作用**,
而一個需要被夾的值,通常本身就已經算錯了。
